## 背景與現況 (Context)

學生分析系統 (Student Analytics System) 被設計為一個邊緣運算 AI 應用程式，
藉由架設於教室中上方的廣角 Webcam 收集關於學生專注度與課堂行為的即時指標。
系統需在資源受限的邊緣硬體上同時完成 AI 推論、資料持久化與即時前端顯示三件事，
這三者在效能、I/O 與記憶體上存在直接競爭，因此架構設計以「解耦」為最高原則。

---

## 目標與非目標 (Goals / Non-Goals)

**目標 (Goals):**

- 提供穩健的即時邊緣 AI 視覺處理框架（硬性維持 5 FPS 處理上限）
- 透過骨架幾何演算法，將推論結果轉化為具意義的專注度分數（0-100）
- 使用 MongoDB Time Series Collection 無阻塞地持久化高頻時序資料
- 提供低延遲儀表板，支援當前課堂即時監控與課後 PDF 報告輸出

**非目標 (Non-Goals):**

- **臉部情緒辨識**：廣角俯瞰下學生人臉像素極小（可能僅 20×20 px），技術上不可行
- **語音辨識或麥克風輸入**：系統僅使用視覺資料
- **企業級雲端部署**：系統優化目標為單一教室的本機或邊緣設備
- **多教室同步監控**：當前版本僅支援單一攝影機輸入
- **學生身份識別**：系統使用匿名 `tracking_id`，不關聯學籍資料

## 架構決策 (Decisions)

### 決策 1：多行程解耦架構（FastAPI + Streamlit 分離行程）

**問題**：Python 的 `cv2.VideoCapture` 在同一系統上只允許一個行程持有攝影機控制權。
若推論後端（佔用攝影機）與前端儀表板在同一行程，存取衝突將造成死鎖。

**決策**：FastAPI 後端作為唯一持有攝影機的行程，以 MJPEG StreamingResponse 推送推論後畫面。
Streamlit 以純 HTTP 客戶端方式消費影像，兩者行程完全獨立。

**取捨**：MJPEG over HTTP 的頻寬略高於 WebRTC，但在局域網下完全可控（5 FPS × 壓縮幀約 30~50 KB/s）。

---

### 決策 2：YOLO-Pose 單一模型取代多模型組合

**問題**：傳統 MediaPipe（per-person）+ DeepFace 組合在 40 人教室中需要 40 次獨立推論，CPU/GPU 必然過載。

**決策**：採用 YOLOv8-Pose（或 YOLOv11-Pose）進行單次前向傳播（Single-pass），
一次偵測全班所有人的骨架節點（COCO 17 keypoints），並以 ONNX Runtime 硬體加速。

**取捨**：放棄情緒辨識（DeepFace），改以骨架幾何代替注意力推斷，技術上更可靠。

---

### 決策 3：骨架幾何取代物件辨識（手機偵測）

**問題**：廣角俯瞰的手機在畫面中可能僅佔 5×8 像素，YOLO 小物件辨識可靠度極低。

**決策**：完全放棄手機物件辨識，改用「手腕 Y 座標高於腰線中點 + 頭部深度俯仰」的幾何規則推斷。

**取捨**：偽陽性率可能高於物件辨識，但 FSM 的 3 秒過濾機制大幅降低誤判影響。

---

### 決策 4：MongoDB Time Series Collection

**問題**：5 FPS 的推論速度意味著每 0.2 秒會為「每一位在座學生」寫入一筆獨立資料。在 40 人滿編班級的 90 分鐘課程中，將產生 `40 × 5 × 60 × 90 = 1,080,000` 筆龐大的時序記錄。
傳統 Collection 的逐筆插入面對每秒 200 筆的併發負荷，會造成極為嚴重的寫入瓶頸與記憶體溢出。

**決策**：`Attention_Metrics` 必須設定為 MongoDB 7.0+ 的原生 Time Series Collection，
並搭配批次插入（`insert_many`，每批 500 筆）減少網路往返。
同時建立 **TTL 索引 (365天)** 自動清理過期高速歷史記錄。

**取捨**：Time Series Collection 不支援任意更新（`update`）操作，
但注意力指標本質上是不可變的歷史記錄，此限制完全可接受。

---

### 決策 5：ONNX 作為強制推論格式

**問題**：PyTorch + ultralytics 運行時佔用記憶體較大，且載入時間長，不適合邊緣設備。

**決策**：所有推論在部署前統一匯出為 `.onnx` 格式，以 `onnxruntime`（或 `onnxruntime-gpu`）執行。
禁止在推論迴圈中動態載入 PyTorch 框架。

**取捨**：部署前需要執行模型匯出步驟（`yolo export format=onnx`），增加一次性準備工作。

---

### 決策 6：信心閾值管理（避免背對鏡頭時的節點雜訊）

**問題**：學生背對攝影機看黑板時，眼鼻節點 confidence 極低但仍有座標值（常常是 [0,0]），直接用這些點計算 Pitch/Yaw 會嚴重失準甚至報錯。

**決策**：統一將 keypoint confidence < **0.45** (`POSE_CONF_THRESHOLD`) 的節點視為無效，並切換至備用計算策略（耳肩幾何），或是拒絕該幀的危險判斷。

**取捨**：備用策略精準度略低，但遠優於使用低信心雜訊節點計算出的錯誤角度。

---

### 決策 7：工業級防禦設計 (Industrial Hardening)

**問題**：伺服器斷電、惡意頻繁請求以及長時間運作下的日誌崩潰。

**決策**：導入全面防禦性設計：

1. **優雅停機 (Graceful Shutdown)**：捕捉 `SIGTERM` 排空寫入佇列 (Queue.join)。
2. **API 速率限制 (Rate Limiting)**：限制敏感端點 (如 PDF 報告生成)。
3. **Trace ID 追蹤**：為每幀賦予獨立 ID，配合結構化日誌以便追蹤排查。
4. **FSM 接關恢復**：系統重啟自動從資料庫讀取未完成的異常事件。

## 風險與取捨 (Risks / Trade-offs)

| 風險                                                 | 嚴重性 | 緩解措施                                                                     |
| ---------------------------------------------------- | ------ | ---------------------------------------------------------------------------- |
| 邊緣硬體過熱導致 GPU 降頻，推論速度 < 5 FPS          | 高     | 鎖定 5 FPS 上限，使用較小 ONNX 模型（yolov8n-pose），降低輸入解析度至 480px  |
| 教室後排學生骨架過小（< 50px），偵測失敗             | 中     | 初期限制 20~30 人中小型教室，記錄未偵測到學生數量於日誌                      |
| ByteTrack 在學生頻繁起身時 ID 重新分配，FSM 狀態丟失 | 中     | ByteTrack 設定 30 幀（6 秒）遮擋容忍；ID 丟失時清除 FSM 並重新初始化         |
| MongoDB 批次寫入失敗導致資料遺失                     | 中     | 最多重試 3 次；若仍失敗則記錄至本地 `.jsonl` 備份檔案                        |
| Streamlit 每秒重新渲染導致 UI 閃爍                   | 低     | 使用 `st.empty()` 容器原地更新，搭配 Plotly 圖表的 `uirevision` 保持縮放狀態 |
